P0-01 — FIX IDEMPOTENCY ARCHITECTURE
==================================================

Inspect:

packages/shared_core/lib/src/local/helpers/id_generator.dart

and backend IdempotencyFilter implementation.

Current risk:

Client-generated sequential/local IDs such as:

BK-YYYY-MM-DD-0001

can collide between different devices/users.

Backend currently must NOT treat only the raw idempotency key as globally unique.

Replace operation-level identifiers with a collision-resistant identifier:

Preferred:
- UUID v7
or
- ULID
or
- UUID v4 if required.

Do NOT use device-local sequential counters as globally unique request IDs.

Backend idempotency identity should incorporate appropriate dimensions such as:

authenticated user
tenant/workshop
branch where applicable
HTTP method
endpoint
idempotency key

Example conceptual key:

SHA256(
  userId +
  branchId +
  method +
  normalizedPath +
  idempotencyKey
)

Do NOT allow:

User A:
POST /sync/repair-orders
key abc

to collide with:

User B:
POST /sync/repair-orders
key abc

or:

User A:
POST /sync/bookings
key abc

Add DB migration if required.

Add automated tests:

SYNC-IDEM-001
same user + same endpoint + same key
=> response replayed safely

SYNC-IDEM-002
different users + same key
=> separate operations

SYNC-IDEM-003
same user + different endpoints + same key
=> separate operations

SYNC-IDEM-004
different branches + same key
=> separate operations

SYNC-IDEM-005
same retry sent multiple times concurrently
=> exactly one business mutation
