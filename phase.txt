==================================================
MARK ONE AS READ
================

Define canonical behavior.

Preferred flow:

user taps notification
→ optimistically mark read locally if safe
→ call backend
→ update shared unread count
→ navigate to destination

OR:

backend then local

depending on repository architecture.

Choose based on correctness.

Requirements:

* no duplicate backend calls
* no race with refresh
* no badge inconsistency
* app restart must preserve read state via backend
* failure must eventually reconcile

==================================================
MARK-READ FAILURE
=================

Do not block navigation to useful content merely because read persistence failed unless architecture requires it.

If navigation succeeds but mark-read fails:

keep/invalidate state so next refresh restores backend truth.

Do not show raw API errors for every failed read marker unless customer action is genuinely required.

Use product judgment.

==================================================
MARK ALL READ
=============

If backend supports mark-all:

wire it.

Requirements:

* loading state
* duplicate-tap protection
* unread count becomes zero on success
* Home badge updates
* refresh keeps everything read
* failure reconciles honestly

Do not loop over each notification client-side if a real bulk endpoint exists.
