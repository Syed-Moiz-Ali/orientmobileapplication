# 5. RESPONSIVE DESIGN — MOBILE, TABLET, WEB, DESKTOP

The entire redesign must support responsive layouts.

Do not make desktop layouts by simply stretching mobile layouts.

Do not make mobile layouts by simply shrinking desktop layouts.

Each form factor must have an intentionally designed experience.

## 5.1 Mobile

Design for small and large mobile screens.

Consider:

- Compact navigation.
- Bottom navigation when appropriate.
- Responsive app bars.
- Prioritized primary actions.
- Touch-friendly controls.
- Adaptive forms.
- Mobile filtering.
- Mobile-friendly record details.
- Bottom sheets for contextual interactions.
- Proper keyboard handling.
- Safe areas.
- Long translated text.
- Scroll behavior.
- Accessible touch targets.

Avoid horizontal overflow and tiny desktop-like controls.

## 5.2 Tablet

Treat tablet as a real form factor, not just an enlarged phone.

Consider:

- Navigation rails.
- Two-column layouts.
- Master-detail patterns.
- Adaptive grids.
- Split-view workflows.
- Larger content regions.
- Landscape and portrait support.
- Contextual side panels.

## 5.3 Web / Desktop

Design for both compact browser windows and large displays.

Consider:

- Professional navigation sidebar.
- Collapsible navigation.
- Header/toolbars.
- Breadcrumbs where useful.
- Responsive grids.
- Data-dense but readable tables.
- Useful sorting and filtering.
- Bulk actions.
- Detail side panels.
- Form layouts.
- Keyboard interactions.
- Hover and focus states.
- Appropriate content maximum widths.
- Efficient utilization of widescreen space.

Do not place all important content on the extreme left of a large display.

Do not stretch content across enormous widths merely because space is available.

## 5.4 Adaptive Behavior

Establish a centralized responsive system.

Define:

- Breakpoint strategy.
- Layout adaptation.
- Navigation adaptation.
- Component adaptations.
- Density differences.
- Typography behavior.
- Overflow prevention.
- Orientation handling.
- Large-screen constraints.
- Minimum supported widths.

Breakpoints must be based on available layout space and actual content needs, not arbitrary device names alone.

Every phase prompt must explicitly specify which responsive layouts must be implemented and tested.

The redesigned application must properly support:

1. English — left-to-right.
2. Arabic — right-to-left.

Localization must be a first-class architectural requirement.

Analyze the existing translation infrastructure and preserve compatibility where possible.

Plan for:

- Full English translation coverage.
- Full Arabic translation coverage.
- Proper RTL layout direction.
- Mirrored directional navigation.
- Correct directional icons.
- Correct text alignment.
- Arabic-friendly typography.
- Dynamic language switching where supported.
- Translation-safe component sizing.
- Long text handling.
- Mixed Arabic/English content.
- Numbers and numeric input.
- Dates and time formatting.
- Currency and units.
- Search and input behavior.
- Form validation messages.
- Dialogs and notifications.
- Tables and data layouts.
- Chart labels where applicable.
- Accessibility labels.

Avoid:

- Hardcoded visible strings.
- Manually reversing every row.
- Assuming Arabic text has the same dimensions as English.
- Translating technical identifiers that should remain unchanged.
- Breaking input behavior in RTL.
- Misaligned directional icons.
- Hardcoded left/right spacing where start/end semantics are needed.

Make RTL correctness a mandatory acceptance criterion in EVERY phase.

A screen is not complete if it only looks correct in English.

# 10. GENERATE DETAILED IMPLEMENTATION PROMPTS

For every identified phase, create a dedicated Markdown file in:

`phases/`

Each file must be a **complete, standalone Codex implementation prompt**, not a short checklist.

Use descriptive filenames with an ordered numeric prefix.

Example:

`phases/PHASE_01_DESIGN_SYSTEM_FOUNDATION.md`

Every phase file must contain:

## A. Phase identity

- Phase number.
- Phase title.
- Objective.
- Priority.
- Dependencies.
- Estimated scope (small/medium/large, without artificial time promises).

## B. Repository context

- Relevant module.
- Relevant screen inventory.
- Relevant file paths.
- Existing architecture to preserve.
- Shared dependencies.

Use real discovered paths, not fabricated filenames.

## C. Design objectives

Describe the exact intended user experience.

Explain how the finished screens should look, behave, and feel.

Do not use vague instructions like "make it modern."

Define actionable visual and interaction expectations.

## D. Screens and workflows

List every screen to be redesigned within the phase.

For each screen explain:

- Screen purpose.
- New visual hierarchy.
- Main sections.
- Navigation.
- Actions.
- Expected interactions.
- Feedback states.
- Components.
- Layout variants.
- Permission-dependent behavior.
- Integration requirements.

## E. Responsive specifications

Explain separately:

- Mobile layout.
- Tablet layout.
- Web/desktop layout.
- What changes between them.
- Navigation adaptations.
- Overflow constraints.
- Orientation considerations.

## F. Localization and RTL

Specify:

- Translation requirements.
- English behavior.
- Arabic behavior.
- RTL mirroring.
- Directional components.
- Formatting.
- Text overflow considerations.

## G. Design system integration

Specify the shared components and tokens that should be used.

Do not permit arbitrary hardcoded styles where reusable design primitives already exist.

## H. Technical implementation

Define:

- Expected code areas to modify.
- New components if needed.
- Existing components to reuse.
- Architecture constraints.
- State management preservation.
- Navigation preservation.
- API compatibility.
- UI integration requirements.

Do not force new packages unless justified.

## I. Functional preservation

Identify behavior that MUST continue working.

Include permission-related and data-related regression considerations.

## J. Testing requirements

Include:

- Static analysis.
- Existing test suite.
- Widget/component tests where applicable.
- Responsive layout tests.
- RTL tests.
- English and Arabic tests.
- Navigation tests.
- Workflow/regression tests.
- Loading/empty/error states.
- Accessibility checks.

Require representative testing across small phone, large phone, tablet, and desktop/web layouts.

## K. Acceptance criteria

Write concrete, verifiable completion criteria.

Examples:

- All screens assigned to the phase are redesigned.
- No horizontal overflow at defined test widths.
- English and Arabic layouts render correctly.
- Shared design tokens are used.
- Existing permissions and workflows remain functional.
- Existing API contracts remain unchanged.
- Loading, error, empty, and success states are covered.
- Relevant automated checks pass.

## L. Deliverables

Specify what Codex must produce after completing the phase:

- Implemented changes.
- Affected file summary.
- Reusable components added or modified.
- Tests executed.
- Results.
- Known limitations.
- Screenshots or visual evidence where tooling supports them.
- Any newly discovered follow-up work.

## M. Completion gate

Require Codex to stop after implementing that phase.

It must not automatically begin the next phase.

Each phase must be independently reviewable and verifiable.
